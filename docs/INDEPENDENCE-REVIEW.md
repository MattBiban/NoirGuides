# Independence review

The record of what was taken from the old fork (the old fork's folder (outside this repository)) and what was looked at there, module by module. The rule is the full build plan's "Independence" constraint: a fork file may be used only when (a) `git log --follow --format=%an -- <file>` shows it was added after the fork's initial import commit, by Matthew Biban, and (b) it contains no code, format or text of the other guide addon. The fork's first commit, `ccf0aaf` (2026-11-08, "Noir Guides 0.1.0"), is the import itself, so every file that existed then fails (a), whoever wrote it.

Task X3 compared every shipped file against the fork; its result is the section "X3: every shipped file". The guide rebuild for 0.2.0 was done in a clean room (nothing of the fork or of the other guide addon was opened); its record is the section "0.2.0: every shipped file" at the end.

## X2: Ports (Menu, Cleanup, Talents, Professions, Diagnostics)

**Result: nothing was ported.** Every fork file that could have served one of the five modules failed rule (a) or rule (b). All of `NoirGuides/Menu.lua`, `Cleanup.lua`, `Talents.lua`, `Professions.lua`, `Diagnostics.lua`, `UI/Panel.lua`, `tools/gen_ports.js`, `tools/lib/talents.js`, `tools/lib/talent_builds.js`, the generated `NoirGuides/Data/Talents.lua`, `Professions.lua` and `Cleanup.lua`, the mock client's additions in `tools/harness/wow.lua` and the tests were written new for this engine, from the plan's one-line description of each module, the spec, the client's own tables and the existing engine's API.

### How the fork was looked at

1. A listing of the fork's root and of `NoirGuides/` (file names only).
2. `git log --reverse` for the first commits, and `git log --follow --format="%h %an %s"` for each candidate file below.
3. `git log --diff-filter=A --name-only` for the files each commit added, and `git show --stat 95b4d2c`, which printed that commit's message along with the file list.
4. For the candidates that passed rule (a): a count and a listing (at most eight lines per file) of the lines matching `addon.`, `addon:` or the other addon's three-letter prefix in either case, to check rule (b).
5. Two files were read in full before their rule (b) result was settled; they are marked below.

### What was seen, and how the new files differ

- **The commit message of `95b4d2c`** (printed by `git show --stat`) describes the fork's profession reading and its cleanup. Facts in it were used only where they are facts about the Forever client, and each was taken again from this project's own sources: the tier lines under each profession (Skinning 2947 under 393) from the client's `SkillLine` table (`tools/gen_ports.js` `loadProfessions`), and the trainer gates 50, 125 and 200 from the full build plan. The fork's profession code was not read.
- *(Superseded by X3: the cleanup was rewritten, see "X3: every shipped file" below.)* **`QuestCleanup.lua`** sorted the quest log into a ticked "off route" group and an unticked "caution" group, protected class, profession, dungeon and epic quests by a generated list and by quest log headers, and abandoned with the client's select, mark, abandon sequence. The new `Cleanup.lua` is built on this engine's `Routes.Current()` and `Progress.Info()` (route format 2), reads the quest log through `State`, and differs where the plan asks: **no row is ever pre-ticked** (the fork pre-ticked off-route quests), each ticked quest is checked again just before it goes, combat stops a run in progress, it keeps no header-based protection (the generated list carries class and profession quests), and it has its own review window from `UI/Panel.lua`. The abandon sequence is the only one the client offers (`docs/ENGINE-NOTES.md` #44).
- *(Superseded by X3: `classifyQuests` was replaced, see below.)* **`gen_quest_protect.js`** classified quests by QuestieDB fields with hand-written quest-sort and instance tables. The new classifier (`classifyQuests` in `tools/gen_ports.js`) uses the same QuestieDB fields, which are QuestieDB's schema (`requiredClasses`, `requiredSkill`, `zoneOrSort`, `startedBy`), but names quest sorts from the client's `QuestSort` table, class and profession names from `ChrClasses` and `SkillLine`, and finds instances with the planner's existing `instanced()` (`tools/lib/quests.js`) instead of a hand list; its output is `Noir.Data.questKeep` and `Noir.Data.questCaution`, plain data in this addon's namespace.
- **Talent builds** were not taken from anywhere: the fork's builds fail rule (a). The nine builds in `tools/lib/talent_builds.js` were written for this project against the Forever trees in the client's `Talent` table, and the generator proves each learnable point by point.
- **Menu and diagnostics**: no fork content beyond the matching lines listed above was seen.

## X3: every shipped file

**Result: three shipped files were rewritten; the other 34 are clean.** The X2 quest cleanup reproduced the fork's design (the generated data matched the fork's `questProtect.lua` entry for entry), so `NoirGuides/Cleanup.lua`, `NoirGuides/Data/Cleanup.lua` and the generator behind it were rewritten on a design of their own. `NoirGuides/UI/Map.lua` wrote a table of game facts in the same form as a library the fork bundles, and now derives it. Everything else the comparison found is a call written the one way the client allows, a one-line comparator, or a game fact.

### Method

`tools/compare_fork.js` (tested in `tools/test/compare_fork.test.js`) reads the fork's 713 tracked files (431 of them text: Lua, XML, toc, JavaScript, Markdown, JSON) and compares every file under `NoirGuides/` with all of them:

- **lines**: a trimmed line of at least 30 characters that occurs in a fork file;
- **exact runs**: a stretch of at least 16 tokens (comments dropped, strings kept) that occurs in a fork file;
- **blind runs**: the same with every identifier and string replaced by a placeholder, at least 48 tokens, so that copied code that was renamed still matches;
- **binary files** (the three textures): SHA-256 against every fork file.

Every lead was then read on both sides. The fork was only read, by that tool and for the leads below; nothing in it was changed. The guide rebuild's clean-room rule forbids opening the fork, so rebuild task X2 deleted `tools/compare_fork.js` and its test (they remain in the git history before that commit). Before then it was run with:

```
cd tools
node compare_fork.js "the old fork's folder (outside this repository)            # what ships
node compare_fork.js "the old fork's folder (outside this repository) --dirs tools,docs
```

### What was found and rewritten

**The quest cleanup (X2).** The first run gave `NoirGuides/Data/Cleanup.lua` exact runs of up to 1,940 tokens against the fork's `NoirGuides/DB/forever/questProtect.lua`: the same quest IDs with the same five labels (`"class"`, `"profession"`, `"dungeon"`, `"epic"`, and `"event"`/`"item"` in a second table). Reading `classifyQuests` in `tools/gen_ports.js` next to the fork's `tools/gen_quest_protect.js` showed why: the same chain of tests in the same order (class mask or class sort, then required skill or profession sort, then instance, then the Epic and Legendary sorts, then event sorts, then item starts), the same "Camping" profession sort, and output tables of the same shape. X2 had read both fork files in full while checking rule (b), and both fail it. The quest facts themselves (which quest needs which class) are QuestieDB's, but the design was the fork's, so it was replaced:

| Part | Before (X2, the fork's design) | After (X3) |
|---|---|---|
| Question | "protect" or "caution" a quest | one question: dropped, can the quest be taken again from its giver? |
| Generated data | `Noir.Data.questKeep[id] = "class"` and `questCaution[id] = "event"`, one verdict per quest, first test wins | `Noir.Data.questTies[id] = { classes = { ... }, skill = N, instance = "name", event = "name", item = "name" }`: every fact that applies, no verdict |
| Class quests | any class quest kept | only the character's own class is left alone; another class's quest is listed by name |
| Profession quests | any profession quest kept, plus the "Camping" sort | left alone only when the character has that profession (Forever's tier lines counted); otherwise listed as "Needs Skinning, which you do not have" |
| Dungeon and raid quests | kept | listed as "can be taken again", naming the dungeon |
| Epic and Legendary sorts | kept | no special case: a giver offers them again |
| Groups in the window | off route, caution | CAN BE TAKEN AGAIN, HARD TO TAKE AGAIN (ready to hand in, event, starting item), each under its own heading |
| Class names | none | the client's own (`LOCALIZED_CLASS_NAMES_MALE`, ENGINE-NOTES #51) |

`tools/gen_ports.js` (`questTies`, `loadQuestTies`, `questTiesLua`) builds the facts from this project's own sources: the planner's class masks (`tools/lib/db.js`, which already reads class quest sorts), `requiredSkill` folded through the client's `SkillLine` tier lines, the planner's `instanced()` and the client's `AreaTable` names, the client's `QuestSort` names for events, and QuestieDB's item names. `NoirGuides/Cleanup.lua` keeps what the plan asks for and what the client dictates (no row pre-ticked, a check again before each abandon, none in combat, the select, mark, abandon calls of #44), and its list building, sorting and window layout were rewritten. The tests (`tools/test/ports.test.js`, `tools/test-lua/cleanup.lua`) were rewritten first for the new behavior. After the rewrite neither file shares a run or a line with the fork.

**`NoirGuides/UI/Map.lua`.** The minimap's yards per zoom level were written `{ [0] = 466 + 2 / 3, [1] = 400, [2] = 333 + 1 / 3, ... }`, the same 36 tokens as `HereBeDragons-Pins-2.0.lua`, a library the fork bundles. The sizes are a fact of the client (ENGINE-NOTES #37), but the notation was the library's, so the table became a function: `(7 - zoom) * 200 / 3`. The existing tests at zoom levels 0, 3, 4 and 5 still pass.

**Tools (not shipped), fixed on the way.** `tools/lib/quests.js` listed the dungeon and raid area IDs in exactly the order of the fork's `gen_quest_protect.js`; they are now in ID order with their AreaTable names (the same set, so no route changes). `tools/lib/characters.js` had the fork's `hasBit` expression and the same character sort expression as the fork's `tools/personas.js`; both are written differently now (BigInt bit test; race, then class), with the same results (`tools/test/characters.test.js`).

## 0.2.0: every shipped file

**Result: 67 files ship; 64 are Clean and 3 are Rewritten (the X3 replacements, still in place). No rebuild task opened the old fork, any code of the other guide addon, or any of its guides.** The 0.1 files the rebuild kept and extended (marked "From 0.1" below) were written before the rebuild, under the earlier rules recorded in the sections above, where the fork was looked at as listed there and nothing was copied; what the rebuild added to them was written from the spec. The guide rebuild (plan `docs/superpowers/plans/2026-11-11-guide-rebuild.md`, tasks C1 to X2) worked in a clean room: the behavior specification `docs/superpowers/specs/2026-11-11-guide-behavior.md` was the only description of how the reference behaves, and the engine, the interface and the route format were written from it, from the rebuild plan, from `DESIGN.md`, from the client's own tables and from QuestieDB. The "port rule" of earlier plans no longer applied: nothing was ported.

### Method

- **Clean room.** No rebuild task opened the fork's folder or the other addon; the comparison tool of X3 (`tools/compare_fork.js`) needed to read the fork, so it was not run during the rebuild and is deleted in X2. There are therefore no comparison leads for the rebuilt files; the files carried from 0.1 keep the leads X3 recorded for them (section above), and their rebuild changes were written from the spec.
- **Name check** (`tools/test/independence.test.js`): no file under `NoirGuides/` or `tools/` (outside the fetched `tools/data/`) contains the other addon's name or its three-letter prefix, in either case. **Result: passes** (1 of 1 test).
- **Clean-room check** (`tools/test/cleanroom.test.js`, new in X2): no file under `NoirGuides/` or `tools/` (outside `tools/data/`) names the old fork's folder; no tool names an absolute path outside the repository (only the 7-Zip and Windows `tar.exe` programs that unpack downloads are allowed); every Lua file under `NoirGuides/` starts with the license line; `Bindings.xml` starts with the license comment. **Result: passes** (5 of 5 tests).
- **Search over the repository:** `git grep -n -i "its prefix\|restedxp" -- NoirGuides tools ':!tools/data'` finds nothing.
