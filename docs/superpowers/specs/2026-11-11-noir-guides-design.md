# Noir Guides: design for the independent addon

Date: 2026-11-11. Status: draft for review.

## Why this exists

The first Noir Guides was a fork of the reference addon (CC BY-NC-SA 4.0). CurseForge rejected it for containing the reference addon's work without the author's permission, and the non-commercial clause rules out ever charging for it. This document describes a new addon that contains no the reference addon code and no the reference addon route, so that neither limit applies.

## Goal

A leveling guide addon for WoW Forever that takes every class and race the client offers (56 combinations) from level 1 to 60, with its own engine, its own guide format and its own routes.

Done means:

1. Every file in the repository is written for this project, generated by this project's tools from licensed data, or a third-party library under a GPL-compatible license with its notice kept.
2. All 56 routes reach level 60 in the simulator with no step a character cannot do.
3. The owner has played at least one starting zone and one mid-level zone in the game and confirmed the window, the arrow and the automation work.
4. The addon is accepted on CurseForge as a new project.

## Ground rules for independence

- Nothing is copied, translated or reworded from the the reference addon fork: no Lua, no guide text, no step order, no data tables (including its flight time table and its map tables).
- The engine is written from this spec and Blizzard's API documentation and UI source. Its structure, guide format and saved variables differ from the reference addon's by design, not by renaming.
- The author of this work has read the reference addon's code while maintaining the fork. This is therefore not a formal clean-room rewrite. The safeguard is the rule above plus a review step: before release, each engine file is compared against the fork for copied structure or text.
- The new repository starts with empty history. The fork's repository is not its ancestor.

## License and data sources

The addon is released under GPLv3.

| Source | What we take | License position |

| Client tables (wago.tools) | Flight points and paths, map and area tables, spells, skill lines, talent trees, character classes and races | Game data read from the client, as addons commonly do. Only facts are used. |

Carried over from the fork, because they were written for Noir and contain nothing of the reference addon's: the Strip Bay design system (DESIGN.md, the textures generator, colors and type), the talent builds and their legality checks, the profession plan, the quest cleanup logic, the menu renderer, the diagnostics, the mock game client and test harness, the client data fetchers, and the route checks that don't depend on the reference addon's format. Each file is reviewed before it is copied; anything that skins or hooks a the reference addon frame is rewritten.

## Architecture

Four parts, each testable on its own.

```
quest + client data ──> route planner ──> route files (Lua data) ──> engine (in game)
                             ^                                          |
                             └──────── simulator and checks <───────────┘
```

### 1. Route planner (build time, Node)

Builds one route per class and race from data.

- **Input:** the quest graph (prerequisites, exclusives, level and race and class limits), where each quest starts, what it needs and where it ends, flight points, and each race's starting zone.
- **Model:** the player's level, position, known flight paths, hearthstone bind, quest log (20 quests) and done quests.
- **Method:** work through zones in level order. Within a zone, group quests by hub, then order pickups, objectives and turn-ins to cut travel (nearest-neighbor with improvement passes), keeping every prerequisite and level limit. Between zones, choose travel from known flight paths, boats and zeppelins.
- **Leveling pace:** quest XP is not in the data, so the planner estimates level from quest levels and counts, and the engine corrects in the game: every step that needs a level carries it, and the engine shows "grind to level N here" when the player is behind.
- **Output:** one route file per starting zone and one per shared level band, in the format below. Deterministic: the same data gives the same routes.
- **Class and race content:** class quests, the profession plan and talent builds are layered in by rules, not by hand-editing routes.

### 2. Guide format (Lua tables)

Routes are plain data, not a script language:

```lua
Noir.Route("horde-undead-01-12", {
  title = "Tirisfal Glades", levels = {1, 12}, faction = "Horde", races = {"Undead"},
  next = "horde-12-20-barrens",
  steps = {
    { action = "accept", quest = 363, at = {zone = 1420, x = 30.2, y = 71.6}, from = {npc = 1568} },
    { action = "kill",   quest = 364, objective = 1, at = {...}, target = {npc = 1501} },
    { action = "turnin", quest = 364, at = {...}, to = {npc = 1569} },
    { action = "train",  spell = 1757, when = {class = "ROGUE", level = 6} },
    { action = "fly",    to = 11 },   -- taxi node ID
  },
})
```

Each step has one action, an optional place and an optional `when` condition (class, race, level, quest state, profession). Text shown to the player is built by the engine from the action and the names in the data, so routes need no hand-written sentences and every locale works from the client's own names.

### 3. Engine (in game, Lua)

Small modules with one job each:

| Module | Job |
|---|---|
| `Core` | Load order, saved variables, events, slash commands |
| `Routes` | Register routes, resolve `when` conditions for this character, chain `next` |
| `State` | What is true now: level, quest log, completed quests, flight paths, professions, position |
| `Progress` | Which step is current; a step is done when the game state says so, never by guesswork |
| `Automation` | Accept and turn in quests, pick gossip options, take flights, set hearth (each can be switched off) |
| `Window` | The Strip Bay window: one lit strip, the rack of upcoming steps, level rail |
| `Arrow` | Direction and distance to the current step's place |
| `Map` | Pins on the world map and minimap |
| `Menu`, `Cleanup`, `Talents`, `Professions`, `Diagnostics` | Ported from the fork's Noir-written modules |

Rules the engine follows: a step is never skipped silently; when the engine moves past a step it records why, and `/noir why` shows it. Nothing is done in combat that the client forbids. No combat log registration, no macro writes, no restyled Blizzard popups (lessons from the fork).

### 4. Simulator and checks (build time)

The existing mock client loads the real engine and plays every route for all 56 characters. A route fails the build when a character is offered a quest it cannot take (level, race, class, prerequisite), is sent on a flight it has not learned, is told to turn in a quest it never had, or does not reach 60. Reports also give each route's total travel distance, so planner changes can be compared by number.

## Build order

1. **Foundation:** repository, license, data pipeline, harness copied in after review.
2. **Engine core** (`Core`, `Routes`, `State`, `Progress`) with tests on hand-written sample routes.
3. **Planner v1** for the six classic starting zones and Zephras Isle, levels 1 to 12.
4. **Window, Arrow, Automation, Map.** First in-game test: the owner plays one starting zone.
5. **Planner v2:** all zones to 60, travel between zones, class and profession layers. All 56 routes pass the simulator.
6. **Ports:** menu, cleanup, talents, professions, diagnostics.
7. **Independence review, then release** on GitHub and as a new CurseForge project.

Steps 2 and 3 are independent of each other and are built in parallel. Step 4's game test happens as early as possible because nothing can be seen outside the game.

## What this will and won't be at first

- Routes will be correct and complete before they are fast. A generated route will not match a hand-tuned speedrun route on day one. It improves through the simulator's travel numbers and through play.
- Dungeons, group quests and Forever-only quests whose data is incomplete are left out of version 1 and listed in a report.
- English first. Other locales follow from the client's own names once the engine is stable.
